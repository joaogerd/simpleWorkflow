# simpleWorkflow TUI 0.6.0 — Design Specification

Date: 2026-09-17  
Target branch: `implementation/tui-0.6.0`  
Base: `83b3e78d904018503310165731170bb357041db4`

## 1. Purpose

Version 0.6.0 refactors the Textual/Rich TUI into an operational inspection tool for scientific workflows, especially long-running HPC/PBS campaigns. The goal is not a cosmetic redesign. The TUI must help the operator move quickly from global workflow state to a selected task, its attempts, scheduler context, logs, files, and failure cause.

The core rule is:

> If information shown in the interface may reasonably invite investigation, the interface should provide a direct way to investigate it.

The implementation must remain a read-only presentation and inspection layer. SQLite remains the source of operational truth. The TUI must not become a second workflow engine.

## 2. Architectural constraints

The following remain unchanged:

- SQLite is the source of truth for workflow state.
- `WorkflowEngine` remains the only execution engine.
- The TUI does not own scheduling or execution state.
- No new daemon, service, socket, REST API, or controller process is introduced.
- No parallel mutable TUI state is introduced to represent workflow truth.
- Restart-safety remains based on persisted state and attempt provenance.
- Local execution and PBS execution retain their current semantics.
- `swf run --ui plain` and automatic fallback remain supported.
- Closing the TUI never cancels the workflow.
- Native cycle state remains authoritative.
- Presentation-only unrolled cycle grouping remains conservative and does not mutate the workflow graph.

No state schema change is required for the TUI refactor.

## 3. Audit findings in 0.5.1

### 3.1 Monolithic presentation layer

`simpleworkflow/tui.py` currently owns layout, state selection, tree rendering, cycle navigation, campaign rendering, problem rendering, Inspector formatting, log selection, log refresh, responsive behavior, and keyboard handling. This concentration makes UI evolution difficult and encourages static widgets rather than reusable operational components.

### 3.2 Inspector is informative but not actionable

The current Inspector is a `Static` widget. It can display task, cycle, status, backend, attempt, timings, command, working directory, PBS job ID, dependencies, outputs, resources, reason, and attempt path, but those values are mostly dead text.

This produces two problems:

- the panel becomes vertically disproportionate;
- important values such as paths, job IDs, commands, and files cannot be acted on directly.

### 3.3 Log view is monitoring-oriented, not investigation-oriented

The current log view uses `RichLog`, which works for tail/follow but is not sufficient for investigation. It does not provide a coherent model for selecting text, copying a path, opening related files, searching, navigating matches, or using the same viewer for JSON/YAML/scripts.

### 3.4 Existing provenance is richer than the TUI exposes

Attempt directories already contain useful structured information:

- `started.json`;
- `metadata.json`;
- `scheduler.json` when applicable;
- `stdout.log`;
- `stderr.log`;
- PBS worker stdout/stderr;
- PBS submission script;
- command, cwd, environment, artifacts, return codes, failure reason, and execution metadata.

The TUI should expose these rather than reconstructing information from free text.

### 3.5 Attempt history is underused

The monitor read model loads attempt history but presents only the latest attempt for each task. Version 0.6.0 must expose task attempt history for inspection without changing execution state.

### 3.6 Layout is still space-driven instead of information-driven

The current Inspector uses flexible height even when it contains only a few fields. Matrix and detail areas therefore compete poorly for space. Header and permanent shortcut text also consume screen real estate that could be contextual.

## 4. Chosen architecture

The preferred architecture is a refactoring of the presentation layer into focused components while preserving `MonitorSnapshot` as the read-only workflow-state boundary.

The TUI is divided into five functional pieces:

1. **Application shell** — global selection, date/cycle navigation, active view, refresh orchestration.
2. **Task/attempt Inspector** — compact task summary, attempt selection, contextual actions.
3. **Resource Browser** — normalized list of files and inspectable resources related to the selected task/attempt.
4. **Text Viewer** — reusable read-only viewer for logs and text files.
5. **Operational overviews** — workflow tree, process/cycle matrices, campaign and problem views.

The main application must coordinate these components through selected workflow context, not duplicate persistent state.

## 5. Read model changes

`monitor.py` remains presentation-oriented and read-only.

### 5.1 Attempt history

Add a stable representation of attempt history for a task. The model may introduce an immutable structure such as:

- task name;
- cycle ID;
- attempt number;
- run ID;
- status;
- return code;
- reason;
- directory;
- start/end timestamps;
- structured command/execution metadata.

The latest attempt remains easy to access for compatibility, but the Inspector must be able to enumerate historical attempts.

### 5.2 Resource representation

Introduce a presentation-level resource descriptor, for example conceptually:

- logical type: stdout, stderr, PBS stdout, PBS stderr, metadata, scheduler, PBS script, declared input, declared output, related file;
- path;
- existence state;
- file/directory kind;
- origin: structured provenance, workflow declaration, controlled log discovery;
- whether it is text-viewable;
- whether follow/reload is meaningful.

This descriptor is read-only. It is not persisted to SQLite.

### 5.3 Structured resources first

Resource discovery priority is:

1. attempt metadata/provenance;
2. scheduler metadata;
3. attempt directory files with known meaning;
4. declared workflow artifacts;
5. conservative path discovery in visible logs.

Free-text log parsing must never override structured provenance.

## 6. Main Monitor layout

### 6.1 Wide terminals

The Monitor uses two primary columns.

Left:
- workflow tree for the currently selected cycle;
- process groups such as OBS/JEDI/MPAS when safely recognized;
- small Workflow group only for global/unclassified tasks;
- task filtering.

Right:
- compact task Inspector;
- attempt/resource actions;
- daily operational process/cycle matrix using remaining vertical space.

The Inspector must use content-sized height rather than consuming a fixed fraction of the panel.

### 6.2 Narrow terminals

Below a width threshold, do not compress both columns.

Default:
- task tree occupies the screen.

Enter or an explicit action:
- opens the selected task Inspector as a dedicated pane/screen.

From Inspector:
- resources and files can be opened without losing task context.

Esc:
- returns one level at a time.

This preserves context rather than switching to unrelated tabs.

### 6.3 Header

The permanent header is compact and operational.

It should prioritize:
- workflow name;
- overall completed/running/failed summary;
- selected date;
- selected cycle;
- live/refresh state.

Run IDs, instance IDs, and other provenance identifiers do not dominate the main screen. They remain available in contextual detail views.

## 7. Inspector design

The Inspector is no longer a long formatted Static block.

### 7.1 Primary summary

Always-visible fields are limited to high-value context:

- Task;
- status;
- cycle/scope;
- selected attempt;
- backend;
- duration or elapsed time;
- return code when available;
- PBS job ID when applicable;
- failure reason when applicable.

### 7.2 Secondary detail

Command, cwd, dependencies, outputs, requested PBS resources, run ID, attempt path, timestamps, and structured provenance are available through expandable/selectable detail sections or contextual actions.

These fields must be copyable.

### 7.3 Attempt navigation

If multiple attempts exist:
- show attempt count;
- allow previous/next selection;
- expose status/time per attempt;
- update files/logs/resources when the attempt changes.

Changing the inspected attempt does not change workflow state or the task selected in the tree.

## 8. Resource Browser

The Resource Browser provides a task-centric list of inspectable resources.

Typical entries:

- stdout;
- stderr;
- PBS stdout;
- PBS stderr;
- `job.pbs`;
- `scheduler.json`;
- `started.json`;
- `metadata.json`;
- declared input/output files that exist;
- related text files safely discovered from logs.

Behavior:

- Enter or click opens the resource;
- `c` copies the resource path;
- missing/disappeared resources are shown as unavailable rather than crashing;
- directories are not recursively browsed in 0.6.0 unless they are required to reach a known file;
- binary files are identified as non-text and are not rendered as garbage.

The browser is contextual to the selected task and attempt.

## 9. Reusable Text Viewer

The viewer is a reusable component/screen for logs and text files.

### 9.1 Required behavior

- vertical scrolling;
- horizontal scrolling or no-wrap mode;
- read-only text selection when supported;
- copy selected text;
- copy current line;
- copy full file path;
- search with `/`;
- next match;
- previous match;
- line/position indication;
- reload;
- Esc to return;
- support files growing while open;
- support follow mode for stream-like logs.

### 9.2 Textual implementation direction

Use Textual's read-only text capabilities rather than implementing an editor. `TextArea(read_only=True)` is preferred when it provides selection and navigation needed by the viewer. `App.copy_to_clipboard` should be used for clipboard actions so no mandatory external clipboard command is introduced.

### 9.3 Structured text

For JSON/YAML and source-like text:
- preserve file content semantics;
- optionally enable syntax-aware presentation when straightforward;
- do not rewrite the file;
- do not pretty-print in a way that hides the persisted content unless the UI clearly labels a formatted view.

The default should favor faithful inspection over transformation.

## 10. Log system

The Logs view becomes an operational instance of the same viewer/resource model.

### 10.1 Stream selection

Available streams are discovered from the selected attempt:
- launcher stdout;
- launcher stderr;
- PBS stdout;
- PBS stderr.

Only streams that exist are offered.

### 10.2 Follow and pause

- follow active: reload file as it grows and keep view at the tail when appropriate;
- paused: preserve operator position while execution continues;
- resume: refresh from disk and optionally return to tail.

### 10.3 Search and copy

Logs support the same viewer actions:
- search;
- next/previous match;
- copy line/selection/path.

### 10.4 Related files from logs

Path detection is conservative.

A discovered path becomes an actionable resource only when:
- the path is absolute or safely resolved against a known cwd/attempt directory;
- it resolves to a regular file;
- access checks do not raise;
- it is not already represented by structured metadata.

Quoted and punctuation-terminated paths must be normalized carefully.

No generic "linkify anything containing /" rule is allowed.

## 11. PBS presentation

PBS is presented as structured scheduler context when recorded.

Possible fields:
- job ID;
- executor;
- queue/resources from task configuration;
- submission script;
- scheduler record;
- PBS stdout/stderr;
- cancellation metadata if present;
- return/exit information actually persisted.

The TUI does not run `qstat` or `qdel` on its own for normal inspection.

It may display scheduler state recorded by the engine, but it must not invent live scheduler state.

## 12. Failures and Problems flow

The Problems view must optimize time-to-cause.

Selecting a failure:
1. establishes the task/cycle context;
2. selects the relevant attempt;
3. prefers stderr/PBS stderr if available;
4. opens the error resource directly when useful;
5. otherwise opens the Inspector with failure reason visible.

From the viewer, the user can then open related files detected from structured provenance or safe log discovery.

Blocked/unknown/invalid-input/invalid-output states remain distinguishable from process failure.

## 13. Cycle and campaign views

### 13.1 Monitor matrix

The compact matrix under the Inspector remains contextual to the selected day. It must use remaining space rather than be squeezed below an oversized Inspector.

### 13.2 Ciclos view

The Ciclos view becomes the broad operational matrix inspired by the useful 0.2.0 behavior:
- process rows;
- actual cycle columns;
- semantic status symbols and colors;
- selection can jump to a cycle/task context.

It must not hard-code 00/06/12/18. It uses actual cycles present in the workflow.

### 13.3 Campanha view

Campanha remains a temporal overview across days and cycles. It should avoid duplicating the exact same information as Ciclos.

## 14. Mouse and keyboard model

The interface must work with both.

Core keys:
- arrows for local navigation;
- Enter to open/inspect;
- Esc to go back;
- Tab/Shift+Tab for focus/view navigation where appropriate;
- `/` for search/filter depending on context;
- `n` / `N` for next/previous search match in viewer;
- `c` for copy contextual value/path;
- `r` for reload/refresh;
- `f` for follow/pause in stream viewer;
- `?` for contextual help;
- `q` closes the monitor only.

Mouse:
- selectable task rows;
- clickable cycle/date controls;
- clickable resource rows;
- clickable tabs;
- clickable log/resource choices.

Help remains contextual and compact rather than a permanent large shortcut bar.

## 15. Copy semantics

Copy must be consistent.

The active context determines what `c` copies:
- resource row -> path;
- Inspector value -> selected value;
- viewer selection -> selected text;
- viewer without selection -> current line, with explicit alternate action for full path.

Where ambiguity would be harmful, the UI may expose explicit "Copy path" / "Copy value" actions.

Clipboard failure must not crash the monitor.

## 16. Responsiveness

At minimum validate:

- 140x40 or larger: full two-column Monitor;
- approximately 100x32: compact two-column or carefully reduced detail;
- approximately 80x24 and below: single-pane navigation.

The design must avoid relying on fixed pixel-like terminal heights for information-heavy panels.

Content must not be hidden behind unreachable widgets.

## 17. File safety and performance

The viewer is for text inspection, not arbitrary file loading.

Rules:
- cap or window large file reads;
- logs may be tailed instead of fully loaded;
- avoid repeatedly scanning large directories;
- avoid repeated expensive stat/read operations for resources not visible;
- tolerate permission errors, races, truncation, replacement, and deletion;
- never follow symlinks into recursive browsing loops because recursive browsing is not part of 0.6.0;
- opening a binary/non-text file shows a clear unsupported message.

HPC shared filesystems must not be polled aggressively.

## 18. Module boundaries

The exact filenames may evolve during implementation, but responsibilities should be separated approximately as follows:

- `tui.py`: app shell, navigation, global selection, top-level composition.
- `tui_inspector.py`: task/attempt Inspector and resource list.
- `tui_viewer.py`: reusable text/log viewer and search/copy/follow.
- `tui_resources.py`: read-only resource discovery and path normalization.
- `monitor.py`: immutable workflow/attempt read model and attempt-history loading.
- tests split by behavior rather than visual snapshots alone.

Do not split files merely for size; each module must have a clear interface and purpose.

## 19. Testing strategy

Tests focus on behavior and contracts, not fragile character-by-character layout.

Required coverage includes:

- task selection;
- cycle/date navigation;
- Inspector context;
- multiple attempts;
- attempt switching;
- stdout open;
- stderr open;
- PBS stdout/stderr open;
- PBS metadata and script resources;
- local task without PBS;
- declared artifacts;
- existing related file;
- missing related file;
- file removed while viewer is open;
- file growing while viewer is open;
- follow/pause/resume;
- viewer search;
- copy path;
- copy selected text/value;
- failure-to-error navigation;
- running task;
- completed workflow;
- blocked/invalid/unknown states;
- narrow terminal navigation;
- wide terminal layout contract;
- task filtering;
- MONAN-JEDI-style unrolled workflow with many tasks;
- restart/reopen from persisted state;
- `swf run --ui plain`;
- auto fallback without TUI dependencies;
- Python 3.10/3.11/3.12;
- Ruff;
- mypy;
- package build and core-only install;
- TUI optional-extra install.

Visual SVG/screenshot demos remain useful as supplemental validation but are not the primary correctness tests.

## 20. MONAN-JEDI validation

The MONAN-JEDI case is a high-value validation target because it stresses:

- hundreds of tasks;
- unrolled scientific cycles;
- OBS/JEDI/MPAS presentation grouping;
- PBS execution;
- long commands;
- many attempt files;
- logs and scheduler output;
- long campaign timelines.

Validation must remain generic: no engine code may special-case MONAN-JEDI.

When live JACI access is unavailable, automated fixtures must represent the structural properties faithfully, and the limitation must be stated explicitly rather than claiming live HPC validation.

## 21. Compatibility

0.6.0 must preserve:

- existing workflow YAML compatibility;
- SQLite schema compatibility;
- local execution;
- PBS execution;
- restart-safety;
- plain reporter behavior;
- optional TUI dependency model;
- `NO_COLOR`;
- read-only `swf monitor`;
- same-process `swf run --ui tui` lifecycle;
- `q` as monitor close, not cancellation.

## 22. Non-goals

0.6.0 does not add:

- workflow mutation from the TUI;
- retry/rerun controls;
- PBS cancel controls;
- an embedded shell;
- a text editor;
- arbitrary directory explorer;
- remote file transfer;
- scheduler daemon;
- REST API;
- persisted TUI preferences;
- MONAN-JEDI-specific execution logic.

These may be separate future features if justified.

## 23. Acceptance criteria

The implementation is complete only when the operator can:

1. identify current workflow/cycle state quickly;
2. select a task with keyboard or mouse;
3. inspect useful task and attempt data without a disproportionate panel;
4. switch among attempts;
5. open stdout/stderr and PBS streams;
6. inspect known metadata, scripts, and related text files inside the TUI;
7. search within opened text;
8. copy paths and selected content;
9. follow growing logs and pause without losing position;
10. reach a useful error stream from a failed task in very few actions;
11. continue using the TUI with large task counts;
12. use a narrow terminal without squeezed side-by-side panels;
13. reopen the monitor and reconstruct state from persisted data;
14. run plain mode unchanged;
15. run without any new workflow-state schema;
16. pass the full automated verification matrix.

The final report must distinguish automated/local validation from any live JACI/PBS validation actually performed.
